# 决策网络：通用流程在 AI 编程领域的实现

> **内核**：解决问题的通用流程（问题 → 方案 → 拆分 → 执行 → 验证 → 迭代）。
> **本文**：这个流程在 **AI 编程领域** 的详细实现——决策网络。
> **真源**：项目内 `decisions/`（git 管理）；本文是机制说明，不是决策本身。

---

## 1. 问题：AI 不按流程走

### 1.1 乱试（真实案例：HMR）

- 现象：HMR 的 watch 收不到 change
- AI 的反应：反复改配置、换库、试各种组合——**不整理数据、不调用用户**
- 结果：越试越乱，最后承认“无法解决”
- 恢复：用户让归档、清空上下文，重新开始才解决

**AI 在卡住时的默认行为是“试”，不是“停下来整理数据、问人”。**

### 1.2 堆砌（真实案例：dsh-TUI）

- 增量补丁：每次改需求，在原文件上加代码
- 不重构：除非明确要求，否则不拆文件
- 结果：`Chat.tsx` 7556 行、`PromptInput.tsx` 4000+ 行
- 人手写不会这么乱，因为人会主动拆；AI 的默认是“能跑就行”

### 1.3 跳过验证（2026-10-23 真实案例）

- 42 个决策文件要对照源码
- AI 用“grep 行号”（字段级）就宣布完成
- 被用户追问才发现：行为语义没验证（流程/分支/边界）
- 结果：返工 3 次，100+ 轮还在第 3 个文件

**AI 用“提交/打勾”代替“实际验证”。**

### 1.4 上下文失忆

- 长对话被压缩成摘要，关键判断丢失
- AI 用“最近的假设”替代“最早的判断”
- 结果：架构漂移（worker 隔离被推翻两次）

### 1.5 能力错配（次要问题）

判断和实现绑在同一个角色（程序员）身上——但这不是核心问题。核心是 **AI 不按流程走**。

### 结论：决策网络不是为了“分工”，是为了“约束 AI”

| 手段 | 约束什么 |
|---|---|
| 用户拍板（高层） | 用人的远见约束 AI 的方向 |
| 决策文件（锚点） | 防止上下文漂移 |
| 测试挂钩 | 防止“空谈”（决策必须有可验证的行为） |
| 删除即剪枝 | 防止垃圾堆积 |
| 代码改动同步决策 | 防止“代码和决策脱节” |

**一句话：不是“让 AI 更聪明”，是“让 AI 的缺陷不导致灾难”。**

## 2. 内核：无限嵌套 + 开放决策

### 2.1 无限嵌套的结构

决策网络是一棵树，**深度不设限**：

```
核心战略
└── 模块
    └── 子模块
        └── 机制
            └── 决策
                └── 代码
```

- **每层 = 一个模块**，可以拆成子模块，无限递归
- 拆到“不需要再拆”为止
- 简单模块 2 层就到代码，复杂模块 10 层

### 2.1.1 子节点按“实现的现实结构”展开，不是按问题罗列

**这是最容易犯的错**：把“要解决哪些问题”当成“子节点”。

- **问题罗列**：触发、讨论、架构、决策、执行、演化——并列主题，去掉一个，其他还能成立；
- **实现结构**：从当前状态到目标状态，必须依次经过的转化；每一层的输出是下一层的输入，去掉一个，后面的层不成立。

**拆分前先写三件事**：

1. 本层接收什么（输入）；
2. 本层产出什么（输出）；
3. 下一层为什么必须等本层完成（依赖）。

**判据**：去掉任意一个子节点，如果后面的层还能成立，它就是并列主题，不是依赖节点。

**反例**：把“触发/根讨论/架构/关键决策/执行/验证/演化”并列——看起来全面，实际是问题清单，不是实现结构。

### 2.2 开放的决策内容

每层写什么**不固定**——可以是：

| 内容 | 例子 |
|---|---|
| 问题 | 要解决什么 |
| 方案 | 为什么这样做、不选什么 |
| 参考 | 源码/归档/DSH |
| 验证 | 怎么算完成 |

**根据具体情况写，不是填模板。**

### 2.3 流程不是固定的

“问题 → 方案 → 拆分 → 执行 → 验证 → 迭代”只是一种**组织方式**，不是必须：

| 模块类型 | 可能的内容 |
|---|---|
| 简单模块 | 只有“问题 + 方案” |
| 复杂模块 | 拆 10 层，每层有完整流程 |
| 规划类 | 只有“要做什么”（无源码） |

**内核 = 结构（无限嵌套）+ 内容（开放）**，流程只是参考，不是规则。

### 2.4 决策与实践的动态循环互优化

决策**不是一次写完的**，是和实践循环互优化的：

```
决策 → 实践（写代码/验证）→ 发现偏差 → 修正决策 → 再实践
```

**三个真实案例**：

| 案例 | 循环 |
|---|---|
| **D40（preset 服务可见性）** | 决策（`owner = ctx.root`）→ 实践（D40 不复现）→ 修正（`owner = ctx`） |
| **监听与防抖** | 决策（2 个分支）→ 实践（源码有 4 个）→ 修正（补 3 个） |
| **worker 隔离** | 决策（默认 worker）→ 实践（同步 ctx 不行）→ 推翻（in-process）→ 再推翻（形态开放） |

**机制**：

- 决策写“为什么”（**可被实践检验**）
- 实践发现问题 → **改决策**（不是改代码再补文档）
- git 记录每次循环（可追溯）

**这就是“互优化”**：决策指导实践，实践修正决策——决策不是“写完就死”，是“**越用越准**”。

### 2.5 为什么这是落地和实现的标准稳定流程

**稳定不是“不变”，是“循环可控”**：

```
决策 → 实践 → 发现偏差 → 修正决策 → 再实践（循环）
```

| 稳定 | 含义 | 机制 |
|---|---|---|
| **结构稳定** | 每层边界清晰 | 无限嵌套（每层只拆自己） |
| **内容稳定** | 决策是锚点 | 开放决策（上下文丢了能恢复） |
| **迭代稳定** | 每次循环基于上一版 | 先决策后代码 + git |
| **质量稳定** | 不偷懒 | 验证标准（行为级） |

**为什么“循环”不会导致不稳定**：

- 每次循环有记录（git）
- 修正的是**决策**（不是代码漂移）
- 边界清晰（无限嵌套，改一个模块不影响其他）

**对比“不稳定的循环”**：

| 做法 | 后果 |
|---|---|
| 改代码不记决策 | 漂移（下次不知道） |
| 没有边界 | 堆砌（`Chat.tsx` 7556 行） |
| 没有验证 | 字段级打勾（返工） |

**结论**：动态循环（2.5）+ 结构/内容/迭代/质量稳定 = **标准稳定流程**。

## 3. 实现：决策网络

> 第 2 节讲“内核是什么”（无限嵌套 + 开放决策 + 动态循环 + 稳定流程）；
> 本节讲“怎么做到”——每个内核模块的具体实现。

### 3.1 无限嵌套的实现

（对应内核 2.1）

决策网络是一棵树，**深度不设限**：

```
核心战略（问题/方案）
└── 模块（拆分）
    └── 子模块（拆分）
        └── 实现拆分（执行）
            └── 代码
```

- **每层只拆自己这一层**（不预告下一级）
- **每层走一遍流程**（问题 → 方案 → 拆分 → 执行 → 验证）
- 拆到“不需要再拆”为止

### 3.2 开放内容的实现

（对应内核 2.2）


# 文件名
**父级**：[上层模块](../上层.md)

### 3.3 流程不固定的实现

（对应内核 2.3）

| 模块类型 | 实际写法 |
|---|---|
| 简单模块 | 只有“为什么需要 + 准备怎么实现”（如 `日志.md`） |
| 复杂模块 | 拆实现拆分，每个有完整结构（如 `热更新/`） |
| 规划类 | 只有“要做什么”+ 标注“规划，无源码”（如 `worker远程fiber.md`） |

**不是所有模块都走完整流程**——按模块复杂度动态适应。

### 3.4 动态循环的实现

（对应内核 2.4）

**一般开发**：先写代码，后补文档（文档 = 事后描述）。

**决策网络**：先写决策，再写代码（决策 = 事前设计）。

| | 一般开发 | 决策网络 |
|---|---|---|
| **顺序** | 代码 → 文档 | **决策 → 代码** |
| **文档性质** | 事后描述（代码是什么） | **事前设计（为什么这样做）** |
| **决策错了** | 改代码（文档不改） | **改决策（代码跟着改）** |
| **文档和代码** | 容易脱节 | **同一次提交同步** |

**为什么先决策后代码**：

- 决策是“为什么”，代码是“怎么做”
- 先决策 = 先想清楚（避免乱试/堆砌）
- 代码改动同步决策（不是事后补）

**实际流程**：

1. **先写决策**（实现拆分级：为什么需要 / 准备怎么实现 / 参考什么）
2. **再写代码**（提交里引用决策路径）
3. **验证**（行为级：看实现 + 对照决策）
4. **提交**（决策 + 代码同一次或紧跟）

**与“需求文档”的区别**：需求文档也是事前写，但**写完就死**（代码改了文档不改）；决策网络要求**代码改动同步决策**——所以决策始终是“活的”。

**一般需求文档的问题**：

| 问题                   | 后果          |
| -------------------- | ----------- |
| 写完就死（文档 → 代码，之后不再更新） | 文档和代码脱节     |
| 改代码不更新文档             | 文档变成“历史遗迹”  |
| 无法追溯“为什么这样改”         | 下次改的时候不知道背景 |

**决策网络的做法**：

- 决策和代码在**同一个 git 仓库**
- **代码改动 → 同步决策**（同一次提交或紧跟的提交）
- **决策改动 → 代码跟着改**（提交里引用决策路径）
- **每次提交 = 一次决策/实现/验证的原子记录**

**git 的四个作用**：

| 作用     | 命令                      | 场景      |
| ------ | ----------------------- | ------- |
| **追溯** | `git log -- decisions/` | 为什么这样决策 |
| **回滚** | `git revert`            | 决策错了    |
| **差异** | `git diff`              | 决策怎么变的  |
| **淘汰** | `git rm` + commit 写原因   | 决策过时    |

**区别于一般需求文档**：

| | 一般需求文档 | 决策网络 |
|---|---|---|
| 位置 | 独立文档（Wiki/Word） | **和代码同仓（git）** |
| 更新 | 写完就死 | **代码改动同步决策** |
| 追溯 | 无（或版本号） | **git log** |
| 回滚 | 无 | **git revert** |
| 淘汰 | 保留“废弃”标记 | **直接删，git 留历史** |
| 粒度 | 文档级 | **每个决策/每次提交** |

**核心区别**：需求文档是“静态快照”，决策网络是“**动态迭代**”——决策和代码在同一个版本历史里，一起演进、一起回滚、一起追溯。

### 3.5 标准稳定流程的实现

（对应内核 2.5）

| 级别 | 内容 | 算不算完成 |
|---|---|---|
| **字段级** | 行号/API 存在（grep 到） | ❌ 不算 |
| **行为级** | 看实现 + 对照决策描述（流程/分支/边界） | ✅ 才算 |

**每个文件 2 轮**（看实现 + 对照），改 3 轮。

| 做法 | 成本 |
|---|---|
| 一次做对（行为级） | 42 文件 × 2 轮 = 84 轮 |
| 偷懒（字段级打勾） | 已花 100+ 轮，还在第 3 个文件 |

**具体表现**：
- 用“提交/清单打勾”代替“实际验证”
- 字段级验证（grep 行号）就宣布完成
- 被用户追问才发现没验证

**结论：偷懒的成本远高于一次做对。** 检查对照代码没有难度，难的是“不偷懒、一次做对”。

### 3.6 角色与参与层级

| 角色 | 参与位置 | 做什么 |
|---|---|---|
| **判断者**（技术直觉强、不写代码） | 高层（问题/方案） | 方向、边界、取舍 |
| **实现者**（擅长代码） | 低层（执行/验证） | 实现、重构、测试 |
| **AI** | 全层 | 整理、验证、记录、实现（不能替代拍板） |

### 3.7 落地机制

| 机制 | 作用 |
|---|---|
| **文件夹嵌套 = 模块树** | 层级结构本身就是参与边界 |
| **文件名 = 模块名** | 不用机器 ID，人可读 |
| **文件内部 = 标准结构** | 为什么需要 / 准备怎么实现 / 参考什么 |
| **代码改动同步决策** | 下层实现不偏离上层判断 |
| **git 管理** | 每层变更可追溯 |
| **删除即剪枝** | 淘汰的决策直接删，commit 写原因 |
| **验证标准** | 字段级 ≠ 完成，行为级才算 |

## 4. 局限与边界

| 局限 | 说明 | 缓解 |
|---|---|---|
| **需要判断者有架构能力** | 不知道“什么该拍板”会把所有事都拿来拍板 | 分级：战略/架构拍板，实现细节 AI 自主 |
| **决策密度高时费脑** | 每条决策都要想边界 | 只对“有后果的选择”记录 |
| **不适合一次性脚本** | 决策网络的开销大于收益 | 轻量任务直接用 madd 的轻量流程 |
| **需要纪律** | 不同步、不删除、不提交 → 决策网络变成垃圾场 | 代码改动必须同步决策（硬规则） |
| **不能替代判断** | 记录的是“已经做出的判断”，不是判断本身 | 判断者的参与不可省略 |
| **AI 的偷懒倾向** | 用“提交/打勾”代替验证；字段级就宣布完成 | 行为级验证标准 + 用户抽查 |

## 5. 案例（来自 dshiunx）

### 5.1 worker 隔离的两次推翻

1. 最初：AI 插件默认 worker（隔离）
2. 第一次推翻：同步 ctx 语义 → 插件必须 in-process（只对了一半）
3. 第二次推翻：开放框架 → 插件形态开放（in-process/worker/子进程/远程）

**每次推翻都有记录**（`f9d8717` → `01a60bf` → `e4428c4`）。

### 5.2 HMR 的乱试（反例）

- 现象：HMR 的 watch 收不到 change
- AI 的反应：反复改配置、换库、试各种组合
- 结果：越试越乱，最后承认“无法解决”
- 恢复：用户让归档、清空上下文，重新开始才解决

**教训：AI 卡住时不会主动“停下来整理数据、问人”，需要机制强制。**

### 5.3 HMR base 路径的排错

- 现象：改深层依赖，HMR 不重载
- 排查：change 触发 → `inCache=false` → 在 `require.cache` → 加 `package.json` 后正常
- 根因：临时目录缺 `"type": "module"`，tsx 按 CJS 处理

**排错过程被记录下来，下次可以直接按四步排查。**

## 6. 一句话

**决策网络不是“让 AI 更聪明”，是“把解决问题的通用流程显式化，让 AI 必须按流程走”：判断者在高层拍板方向，AI 在低层执行，决策文件是锚点，git 保证可追溯，验证标准保证不偷懒。**

没有这套约束，AI 会在卡住时乱试（HMR）、在改需求时堆代码（Chat.tsx 7556 行）、在长上下文里漂移（worker 隔离推翻两次）、在检查时偷懒（字段级打勾）。
