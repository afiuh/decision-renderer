# 决策网络 vs 社区开源框架：对比

> **对比对象**：GitHub Spec Kit、BMAD Method、Claude Code Skills（Agent Skills 标准）
> **目的**：看清我们的独特之处，以及别人值得借鉴的地方
> **时间**：2026-10-22

---

## 1. 四个框架的核心

| 框架 | 核心抽象 | 一句话 |
|---|---|---|
| **GitHub Spec Kit** | **spec（规格）** | Specify → Plan → Tasks → Implement → Converge，每个阶段产出 Markdown artifact |
| **BMAD Method** | **角色 + 故事** | PM / Architect / UX / Dev / QA 五个 AI 角色，规划先行，BMad Loop 无人值守执行 |
| **Claude Code Skills** | **skill（指令包）** | `SKILL.md` 按需加载，Agent Skills 开放标准，`/doctor` 检查过时指令 |
| **我们（决策网络）** | **决策（为什么）** | 无限嵌套的模块树，决策文件记录“为什么这么定”，删除即剪枝 |

---

## 2. 对比维度

| 维度 | Spec Kit | BMAD | Claude Skills | 决策网络 |
|---|---|---|---|---|
| **结构化** | 固定阶段（5 步） | 固定角色（5 个） | 按需加载 | **无限嵌套**（深度不设限） |
| **记录什么** | spec（代码长什么样） | 规划文档 + 故事 | 指令/流程 | **决策（为什么长这样）** |
| **淘汰机制** | 无（spec 迭代） | 无 | `/doctor` 检测过时 | **删除即剪枝 + commit 写原因** |
| **角色** | 单 agent | AI 扮演多角色 | 单 agent | **人判断 + AI 执行** |
| **追溯** | spec 历史 | story/run 历史 | git | **git log decisions** |
| **适应粒度** | 固定流程 | 固定角色 | 按需 | **无限层级，具体情况具体分析** |
| **代码同步** | spec 可能漂移 | 规划可能漂移 | 无强制 | **代码改动必须同步决策（硬规则）** |

---

## 3. 我们的独特之处

### 3.1 无限嵌套（别人都是固定阶段/角色）

- Spec Kit：5 个固定阶段（Specify/Plan/Tasks/Implement/Converge）
- BMAD：5 个固定角色（PM/Architect/UX/Dev/QA）
- 我们：**深度不设限**，一个模块可以拆 3 层，也可以拆 10 层

**为什么重要**：固定阶段/角色会逼着简单模块“削足适履”，复杂模块“细节丢失”。

### 3.2 决策可淘汰（别人没有）

- Spec Kit / BMAD：没有“淘汰”机制，旧 spec/故事会堆积
- Claude Skills：`/doctor` 能检测过时指令，但不删除
- 我们：**删除即剪枝**——过时决策直接删，commit 写原因（取代者/影响面）

**为什么重要**：树始终干净，不留“已废弃”垃圾；git 历史保留现场。

### 3.3 判断与实现分离（BMAD 是 AI 扮演角色）

- BMAD：AI 扮演 PM/Architect/Dev，**判断也是 AI 做的**
- 我们：**人做判断（高层），AI 做执行（低层）**

**为什么重要**：AI 的判断力有缺陷（乱试、堆砌、上下文漂移），不能让它扮演“架构师”；人做判断，AI 执行。

### 3.4 代码改动必须同步决策（硬规则）

- Spec Kit：spec 和代码可能漂移（spec 是“预先写的”，代码是“后来写的”）
- 我们：**代码改动必须同步决策**（改了 loader 就补插件加载的决策）

**为什么重要**：防止“决策和代码脱节”，决策网络始终是活的。

## 4. 别人值得借鉴的地方

### 4.1 Spec Kit 的 artifact 链

- Specify → Plan → Tasks → Implement → Converge，每个阶段有明确的产物
- **可借鉴**：我们的决策文件可以借鉴“阶段产物”的思路——比如“战略文件”和“实现文件”有不同的模板

### 4.2 BMAD 的角色分工

- PM / Architect / UX / Dev / QA，每个角色有明确的职责
- **可借鉴**：我们的“判断者/实现者”可以再细分（产品判断/架构判断/实现/测试）

### 4.3 Claude Skills 的按需加载

- `SKILL.md` 的 body 只在用的时候加载，节省上下文
- **可借鉴**：决策文件也可以“按需加载”——不是所有决策都要一次读进上下文，按当前任务加载对应模块

### 4.4 Claude 的 `/doctor prompt-audit`

- 自动检测 CLAUDE.md/skills 里的过时或冲突指令
- **可借鉴**：我们可以做一个“决策审计”工具——扫描决策文件，检测：
  - 引用了已删除的文件
  - 与代码不一致的决策
  - 长期未更新的“待定”

---

## 5. 结论

### 5.1 我们的位置

| 框架 | 解决的问题 | 我们的差异 |
|---|---|---|
| Spec Kit | “先写规格再写代码” | 我们记录“为什么”，不是“长什么样” |
| BMAD | “AI 扮演团队角色” | 我们让人做判断，不让 AI 扮演 |
| Claude Skills | “指令按需加载” | 我们按模块树组织，不是按 skill 包 |

### 5.2 一句话

**社区框架在解决“怎么让 AI 按流程写代码”；我们在解决“怎么让 AI 的判断力缺陷不导致灾难”。**

前者是“流程工程”，后者是“判断工程”。

### 5.3 下一步可借鉴

1. **决策审计工具**（借鉴 `/doctor prompt-audit`）：扫描死链、不一致、长期未更新
2. **按需加载**（借鉴 Claude Skills）：按当前任务加载对应模块的决策
3. **角色细分**（借鉴 BMAD）：判断者可以再分产品/架构/测试
