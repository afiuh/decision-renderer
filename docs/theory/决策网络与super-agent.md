# 决策网络 × Super-agent：当结构成为智能的载体

> 草稿 · 2026-11-06
> 材料来源：DeepSeek Harness 官方文章《Super-agent 设计探索：迈向更自主的 Agent 系统》（2026-10-31）、`dsh-superagent-prototype` 源码（19.3k stars，TypeScript，12,390 行）、以及本项目（dshiunx）的决策网络实践。

## 一、问题：智能体的三个天花板

过去一年，Coding Agent 证明了模型能用工具解决复杂问题。但把规模放大——多任务、团队协作、长期运行——三个天花板立刻出现。

### 1.1 上下文：寿命的天花板

Agent 的工作模式以单一 Session 为基本单位。Session 里塞着历史、工具调用、推理过程。跑几天，上下文爆了，必须压缩、重启、丢记忆。

**结果**：智能体的"寿命"被上下文窗口锁死。它不是"能一直干"，是"能干到窗口满为止"。

### 1.2 理解：规模的天花板

项目变大后，Agent 需要"理解整个项目"——读几十个文件、保持长上下文。但上下文越长，越难保持整体；用户一纠正，就局部修，越修越碎。

**结果**：智能体的"能力上限"等于"模型能理解多少"。模型不能无限大，所以项目不能无限大。

### 1.3 协作：接口的天花板

多 Agent 协作靠"消息"（MCP / A2A 协议）。但每个 Agent 的上下文是隔离的，接口不统一——A 知道的，B 不知道；A 的"完成"，B 不认。

**结果**：协作成本随 Agent 数量平方增长（两两对齐）。

### 1.4 三个天花板的共同点

它们都不是"模型不够聪明"，是"**结构缺失**"：

| 天花板 | 缺什么结构 |
|---|---|
| 上下文 | 记忆没有外置（全在窗口里） |
| 理解 | 知识没有分层（全在上下文里） |
| 协作 | 接口没有统一（全靠消息） |

## 二、Super-agent：野心与实现

DeepSeek Harness 团队在 2026-10-31 发布文章《Super-agent 设计探索》，并开源了 `dsh-superagent-prototype`（19.3k stars）。

### 2.1 四个特征

文章定义 Super-agent 的四个基础特征：

| 特征 | 含义 |
|---|---|
| **连续** | 用户可以在 IM、GitHub 等熟悉界面交互，感觉始终只有一个 Agent |
| **高效** | 并发、高质量完成多个复杂任务，不等上一条命令 |
| **主动** | 持续观察环境事件，主动推进，不需要 @ |
| **持久** | 始终在线，长期运行遇异常自动恢复 |

> 单个 ReAct Loop 无法同时支持这四个特征。

### 2.2 双层架构

```
Router 层（常驻）
  ├─ 承接所有人类交互
  ├─ 全局记忆与协调
  ├─ 不执行具体任务（甚至不配 Bash）
  └─ 分派任务给 Worker
        ↓
Worker 层（隔离，并发）
  ├─ 上下文隔离
  ├─ 挂完整工具
  ├─ 专注单一任务
  └─ 不直接与人交互，向 Router 汇报
```

**核心权衡**：连续性与吞吐量。

- 所有事件交给同一个 Session → 上下文最连续，但串行、吞吐低
- 每条事件新开 Session → 吞吐最高，但上下文割裂、交互混乱

**双层架构**：Router 保连续，Worker 保吞吐。

**批处理**：Router 上一轮推理期间积压的 Trigger，下一轮合并注入——"积压越多，单个决定分摊的推理时间越低"。

**关键洞察**：

> Session 应当是系统的实现细节，而不是用户的认知负担。

### 2.3 事件驱动

#### 2.3.1 事件过滤（Fast Path / Slow Path）

- **程序层**（Fast Path）：来源、群组、白名单等确定性条件，代码直接准入
- **语义层**（Slow Path）：通过准入的候选事件交给 LLM 判断

#### 2.3.2 事件路由（订阅直通）

- **已订阅**（Fast Path）：同一 Thread 的后续事件由程序直通已订阅的 Worker，不经 Router
- **未订阅**（Slow Path）：Router 判断和分派新事件

#### 2.3.3 上下文组织（Inline & Spill）

- **Inline**：近期很可能用到的信息直接内联
- **Spill**：超出窗口预算或低频使用的信息留在窗口外，只保留引用/摘要

**具体量化**（`src/app/assessment.ts`）：

```ts
const TRIGGER_CHARS = 4000, NEAR_CHARS = 1200, WINDOW_CHARS = 400, STUB_CHARS = 50
```

**cards 投影**（`src/app/cards.ts`）：

```ts
{ trigger_id, source, actor, thread, human, at,
  preview: preview(trigger.text),   // 160 字
  chars: trigger.text.length,
  read: `trigger/${trigger.id}` }   // 按需读取
```

#### 2.3.4 提前行动（投机执行）

- 后台先尝试，有价值就交付，没有就丢弃
- 例："静默复现并修复"策略——群里有反馈时，后台先复现、找修复，确认后才交付

### 2.4 面向人的交互

#### 2.4.1 全双工（异步 ReAct Loop）

- 经典 ReAct：`run()` 同步阻塞，工具执行完才返回
- 异步 ReAct：`run()` 立即返回 `Started`，后台完成作为新事件投递；`cancel()` 终止长命令

> 这一异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。

#### 2.4.2 多信道

- **IM**：低打扰，只问直接问题，单次回复 ≤100 词
- **GitHub / 邮件 / 文档**：结构化、高信息密度（问题背景、改动说明、验证结果）

### 2.5 计算、状态与环境的分离

#### 2.5.1 计算与状态分离

- Agent Loop 无状态（云端弹性容器）
- Session 状态持久化（数据库）

#### 2.5.2 计算与执行环境分离

- 环境留在原地（端侧轻量 daemon）
- 支持 BYOM（Bring Your Own Machine）

### 2.6 Watchdog（外部 Control Loop）

- 独立 Session，定时消息驱动
- 检查：基础设施故障 + **任务进展/方向**（模型判断 Worker 是否有实质进展、是否偏离目标）
- 可用自然语言询问故障、在线修正主系统

### 2.7 部署形态：独立 bundle / profile

`dsh-superagent-prototype` 本身就是一个 DSH bundle（`cordis.patch.yml` + `package.json`），但部署为**独立 profile**（`superagent`）：

> **A dedicated DeepSeek Harness profile**... Keep it separate from the profile you work in: the plugin changes **process-wide `PATH` and git settings**, and its process needs **independent restarts and upgrades**.（`docs/006-deployment.md`）

**原因**：

| 原因 | 说明 |
|---|---|
| 改进程级 PATH | 注入 `gh` / `lark-cli` 包装器 |
| 改 git 设置 | 设置 git 身份/提交邮箱 |
| 独立重启/升级 | 研究原型频繁重启，不能影响日常 profile |

### 2.8 代码事实

#### 2.8.1 领域概念写死

`src/core/model.ts` 定义了 14 个概念（全部是 TypeScript interface）：

```
ActorRef / ThreadRef / ChannelRef / Trigger / TriggerDisposition
Strength / AdmissionCell / AcceptMode / MandateBasis / Mandate
Evaluation / Thread / DecisionKind / Decision
AssignmentState / ReportState / Assignment / TicketInput / PolicyEffect
TicketEndBy / TicketOutcome / Attention / Ticket / Follow / Execution
```

**加一个新概念** = 改 `model.ts` + `store.ts`（SQLite schema）+ `engine.ts` + `client/`。

#### 2.8.2 扩展点只有三个

`src/core/ports.ts`：

| 扩展点 | 能换什么 |
|---|---|
| `Source` | 加新来源（GitHub/飞书 → Slack…） |
| `Assessor` | 换评估模型 |
| `Executor` | 换执行器 |

#### 2.8.3 架构质量

| 维度 | 评分 | 依据 |
|---|---|---|
| **分层** | 9/10 | `core` 纯（只依赖 `./model`/`./ports`/`./errors`/`./ids` + `node:crypto`）；`core` 不依赖 `app`（grep 空） |
| **耦合** | 6/10 | `app` 直接 import `DshExecutor`（具体类）、`github-read`（具体 source）、`executor` 的工具函数 |
| **可扩展** | 5/10 | 只有 3 个扩展点；领域概念写死 |
| **可维护** | 8/10 | `migration.ts` 616 行 + `SCHEMA_VERSION` + `tests/` + `pnpm check` |
| **规模** | 合理 | 13,599 行（core 2,000 / app 3,500 / client 1,222 / executor 700 / sources 3,000） |

**明确妥协**：

| # | 妥协 | 影响 |
|---|---|---|
| 1 | `app` 直接 import `DshExecutor`（类，不是接口） | 换 Executor 要改 app |
| 2 | `app/assessment.ts` import `readRepositoryPath`（GitHub 具体） | 换 Source 要改 app |
| 3 | `app/cards.ts` import `executor/dsh.ts` 的 `batchLine` / `inputResource` | app 依赖 executor 内部函数 |
| 4 | `executor/dsh.ts` 673 行 | 大文件（PrepareFailed / WorkerSlots / DshExecutor 混在一起） |

### 2.9 原型边界：4 个未实现的设计

README 说："Some designs discussed in the article are directions for future development and are not implemented in this prototype."

**grep 验证**（`src/` + `docs/`）：

| # | 设计 | 文章位置 | grep 结果 |
|---|---|---|---|
| 1 | **Watchdog**（外部 Control Loop） | 第 6 节 | `watchdog` → **0 命中** |
| 2 | **投机执行**（提前行动） | 3.4 节 | `speculative` / `提前` → **0 命中** |
| 3 | **链式召回**（Chain of Recall） | 3.3 节 | `chain.*recall` → **0 命中**（只有 Inline & Spill） |
| 4 | **计算/状态/环境分离** | 第 5 节 | 单机 SQLite + 本地 executor，无云端/daemon |

**已实现**：双层架构、事件过滤、订阅直通、Inline & Spill、多信道、批处理、异步后台 job。

**为什么没实现这 4 个**：

| 设计 | 原因 |
|---|---|
| Watchdog | 运维层（独立 Session + 定时驱动），不是核心域 |
| 投机执行 | 成本高（算力），容易产生噪音（违背"最少注意力"） |
| 链式召回 | 上下文层优化，`Inline & Spill` 已经够用 |
| 分离 | 需要云端基础设施（容器 + 数据库 + 端侧 daemon） |

## 三、决策网络：结构即上下文

### 3.1 一体多面

决策网络是同一个机制，在不同层面解决不同问题：

| 面 | 机制 | 改善什么 |
|---|---|---|
| **结构面** | 父子关系（根 → 模块 → 子模块） | 逼你**先分层再钻细节** |
| **记忆面** | 节点 = 结论（外置） | 逼你**把结论写下来** |
| **决策面** | 每个节点记"为什么存在" | 逼你**先问为什么** |
| **验证面** | 每个节点有"验证" | 逼你**先定验收** |
| **约束面** | 每个节点有"边界" | 逼你**先划边界** |
| **协作面** | 人类定根/拍板 | 逼你**承认不知道** |
| **演进面** | git 历史 | 逼你**留痕** |

**所有面都是同一个操作**：写/读一个节点。

### 3.2 现实做事的标准结构

```
目标（为什么做）
  → 分解（模块/子模块）
    → 边界（不做什么、限制）
      → 验证（怎么算完成）
        → 执行
          → 反馈（更新节点）
```

**从"吃什么"到"航母建造"都是这个结构**：

| | 今天吃什么 | 航母建造 |
|---|---|---|
| 目标 | 吃饱/健康/省钱 | 作战能力 |
| 分解 | 主食/菜/饮料 | 船体/动力/电子/舰载机 |
| 边界 | 预算/时间/忌口 | 预算/工期/法规/技术 |
| 验证 | 好吃/饱 | 海试/演习 |
| 执行 | 做饭/点外卖 | 船厂/供应链 |
| 反馈 | 不好吃 → 调整 | 问题 → 返工 |

### 3.3 事件是结构的一部分

| 传统理解 | 决策网络 |
|---|---|
| 事件 = 外部输入（Trigger） | 事件 = **节点的状态变化**（"饿了"是目标节点的输入） |
| Thread = 事件流 | Thread = **节点的历史**（同一节点的状态变化序列） |
| Router 分派事件 | **节点自己决定**（边界内就执行，边界外就阻塞） |

### 3.4 推演，不是分类

**关键区别**：

| 分类（错） | 推演（对） |
|---|---|
| 把章节装进节点 | 把**推演步骤**装进节点 |
| 节点 = 章节标签 | 节点 = "**为什么能推出**" |
| 结构 = 分类树 | 结构 = **因果链**（A → 因为 X → B） |

**节点的"为什么存在" = 上一步的遗留问题**：

```
节点 N 的"为什么存在" = 上一步的什么问题
节点 N 的"输入" = 上一步的结论
节点 N 的"输出" = 下一步的输入
节点 N 的"边界" = 不能违反的上一步结论
```

## 四、融合：从"事件驱动"到"结构驱动"

### 4.1 概念映射

| super-agent | 决策网络 |
|---|---|
| Router 的全局记忆 | **节点树本身** |
| Ticket | 任务节点 |
| Mandate | 节点的"授权"字段（谁定的、边界、强度） |
| Eval | 读节点 + 判断（边界内吗） |
| 阶段（等待什么） | 节点状态（待确认/执行中/完成/阻塞） |
| Subscription | 节点订阅（同一节点的变更通知相关 Worker） |
| Thread | 节点的事件流（Trigger 落到节点） |
| Policy | 节点的"边界 + 验证" |
| Watchdog | **偏离检测**（Worker 是否越界、节点是否过时） |

### 4.2 角色与结构

**super-agent 的 Router/Worker 是"角色"，决策网络的节点是"结构"**：

- **角色**（Router/Worker/Watchdog）= 操作节点树的**不同方式**
- **结构**（节点树）= 所有角色共享的**唯一真源**

**Router 读节点树做分派，Worker 读节点做执行，Watchdog 读节点做检查**——三者不需要"传上下文"，因为**节点树就是上下文**。

### 4.3 会发生什么

**super-agent 从"事件驱动的多会话系统"变成"结构驱动的单一真源系统"**——所有 agent 操作同一棵节点树，上下文、授权、验证、协作全部由结构承载。

## 五、决策网络 vs Super-agent：结构即数据

### 5.1 代码事实

| | super-agent | 决策网络 |
|---|---|---|
| **结构** | 14 个 interface 写死在 `model.ts` | **节点文件** |
| **加概念** | 改 `model.ts` + `store.ts` + `engine.ts` + `client/` | **加一个节点文件** |
| **扩展点** | 3 个（Source/Assessor/Executor） | **无限**（加节点/加子树） |

### 5.2 决策网络能做到、它做不到（6 条）

| # | 能力 | 为什么 |
|---|---|---|
| 1 | **结构即数据**（加概念不改代码） | 它的结构是 TypeScript interface |
| 2 | **跨项目移植** | 它绑定"一个 GitHub 仓库"（`Source` 是 GitHub/飞书） |
| 3 | **理解结构化**（为什么/边界/验证） | 它的 `Ticket` 是"工作单元"（title/scope/mandate） |
| 4 | **多 agent 共享结构** | 它的 Worker 上下文隔离，共享的是"事件"（Thread 订阅） |
| 5 | **人类定根** | 它的 `Policy` 是规则（allowed list/accept mode），不是"根节点" |
| 6 | **测试追溯** | 它的 `Decision` 是判断记录，不是"验证锚点" |

111111111111### 5.3 它做到、决策网络要补（5 条）

| # | super-agent | 决策网络要补 |
|---|---|---|
| 1 | **事件驱动**（Trigger 流） | "事件 → 节点"的映射 |
| 2 | **订阅直通**（Thread → Worker） | "节点订阅" |
| 3 | **批处理**（Router 积压合并） | 没有"批处理"概念 |
| 4 | **Slot**（并发控制 + 人的额外 slot） | 没有"slot"（可以借） |
| 5 | **Watchdog**（外部 Control Loop） | 可以借（节点即检查标准） |

### 5.4 结论

**它不是竞争对手，是"运行时"**；决策网络可以是它的"**数据层**"（节点树替代 Ticket/Mandate/阶段），它的 Source/Executor/Watchdog 仍然有用。

## 六、能实现什么（之前不敢想的事）

### 6.1 上下文无关的长期运行

现在：agent 跑几天，上下文爆了，必须压缩/重启/丢记忆。

决策网络：agent 不"记住"任何东西，只读节点——**可以跑几年**（上下文不增长，节点树增长）。

> **智能体的寿命不再受上下文窗口限制。**

### 6.2 多智能体真正并行

现在：Router 分派 → Worker 执行（仍是"一个任务一个 Worker"，任务间耦合靠 Router 协调）。

决策网络：**N 个 agent 各负责一个子树**，节点边界 = 职责边界——不需要 Router 协调（边界不重叠）。

> 从"一个老板带一群工人"变成"每个模块一个负责人"——**并行度 = 节点数**。

### 6.3 人类从"执行者"变"立法者"

现在：人参与细节（纠正、拍板、验收）。

决策网络：人只定**根**（目标/边界/验证）和**拍板**（待确认节点）——细节由 agent 展开。

> 人的角色从"做事"变成"立法"——**一个人的产出 = 一棵树的产出**。

### 6.4 可审计的智能

现在：agent 的行为是黑箱（为什么这么做？不知道）。

决策网络：每个动作对应节点，节点有 git 历史——**智能体的每个决策都可追溯、可回滚**。

> 智能体不再是"黑箱"，是"**有案卷的公务员**"。

### 6.5 A2A 通用协议

现在：多 agent 协作靠"消息"（MCP/A2A），接口不统一。

决策网络：**节点边界就是接口**——任何 agent（不同模型/公司）读同一棵树就能协作。

> 协作不需要"协议"，只需要"**同一棵树**"。

### 6.6 小模型做大事

现在：agent 的能力 = 模型能力（上下文理解）。

决策网络：**结构承载理解**（节点写清楚），模型只负责执行——小模型也能做复杂项目。

> 瓶颈从"模型"转移到"结构"——**结构可以无限扩展，模型不能**。

### 6.7 测试范式变化

现在：测试 = 跑代码，失败 = 翻代码找 bug。

决策网络：测试 = 验证节点的"完成标准"——失败 = 某个节点没过，定位到节点。

> 从"测实现"变成"**测承诺**"（节点承诺了什么）。

### 6.8 跨项目移植

现在：每个项目从零开始（重新理解、重新设计）。

决策网络：节点树可以**复制/合并**——"航母建造"的结构可以移植到"软件开发"。

> 经验不再"沉淀在人脑"，而是"**沉淀在结构**"。

## 七、实验：决策网络如何增强理解

### 7.1 对象

`任何不符合现实的观点和理论都与宗教同构.md`（1224 行，31,538 字）。

### 7.2 直接理解

估计 **3-5 轮**：用户补背景 → 我分类 → 用户纠正"不是分类" → 我重来。

**问题**：读到"九、性价比"时，"五、构造性"已经模糊；读到"十一、饭圈"时，前面的"三个节点"记不清。

**不是读不懂，是记不住。**

### 7.3 决策网络

**第一轮（错）**：把 12 节分成 7 个模块（定义/同构/构造/门槛/性价比/案例/死穴）——**分类套壳**。

**用户纠正**："你还是只是分类套壳而已，你看不出推演逻辑吗"。

**第二轮（对）**：展示推演链：

```
根：为什么同构但不同等？

观察：宗教 7 特征 / 不符合现实的 7 特征 → 完全相同

推 1：为什么相同？
  → 都源于同一个机制：循环论证 + 强化范畴
  → 循环论证 → 必须长出"不可证伪的核" + "叙事替代论证"
  → 强化范畴 → 必须长出"解释权垄断" + "情感入口" + "服从机制" + "群体边界"
  → 解释权 + 服从 → 必须长出"利益闭环"

推 2：为什么不同等？
  → 门槛一：一次性提供全套实现标准（5 组需求）
  → 门槛二：认知重塑活化能低（领导者能力）

推 3：为什么性价比不同？
  → 门槛越高，跨过后的收益越大

推 4：案例验证
  → 饭圈：门槛二上不去 → 上限被锁死
```

### 7.4 对比

| | 直接理解 | 决策网络 |
|---|---|---|
| **轮数** | 3-5 轮 | 2 轮（第一轮错，纠正后对） |
| **单位** | 词/段 | **推演步骤** |
| **记忆** | 靠上下文（读到后面忘前面） | **结构**（每步的输入/输出/为什么） |
| **理解** | "这段话在说什么" | "**这一步从上一步推出了什么**" |
| **复述** | 复述内容 | **复述推演** |

### 7.5 结论

**决策网络增强理解的关键不是"拆得更细"，是"先建根 + 展示推演"**——没有根，读到的都是"词"；有了根，每个词都知道它在回答什么；没有推演，读到的都是"分类"；有了推演，每步都知道"为什么能推出"。

## 八、难点（诚实）

| # | 难点 | 说明 |
|---|---|---|
| 1 | **并发写** | 多个 agent 改同一棵节点树——锁、版本、冲突、合并 |
| 2 | **节点粒度** | 太粗 → agent 不理解；太细 → 碎片化（几百个节点，没法读） |
| 3 | **"理解"怎么验证** | agent 说"读了节点"，但理解对吗？——不是 grep 到就算 |
| 4 | **测试锚点** | 测试怎么对应到节点？一个测试跨多个节点怎么办？ |
| 5 | **一致性** | 改了代码没改节点 / 改了节点没改代码——怎么保证同步 |
| 6 | **元层怎么"跑"** | 机制是文档还是循环里的 gate——还没定 |
| 7 | **失败放大** | 节点写错 → 所有读它的 agent 一起错（比单 agent 更危险） |

## 九、结语

> 现在智能体的上限是"**模型能理解多少**"，决策网络的上限是"**结构能组织多少**"——前者有天花板，后者没有。

super-agent 已经把"运行时"做到了很高的水平：双层架构、事件驱动、订阅直通、Inline & Spill、批处理、异步 ReAct、Slot、Watchdog（设计中）。

决策网络不替代它——**决策网络是它的"数据层"**：

- 它的事件 → 节点的状态变化
- 它的 Ticket → 任务节点
- 它的 Mandate → 节点的授权
- 它的阶段 → 节点的状态
- 它的 Watchdog → 节点的偏离检测

**融合后，super-agent 从"事件驱动的多会话系统"变成"结构驱动的单一真源系统"**——所有 agent 操作同一棵节点树，上下文、授权、验证、协作全部由结构承载。

这不是"设计"出来的，是**长**出来的。现在只是图景。
